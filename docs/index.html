opencode-loopd spawns an autonomous child session per goal and drives it with accumulated context. The parent chat stays free. Completion is host-verified — checks must pass, not just be claimed. Concurrency is ticketed like an OS: files are claimed, writers wait and wake, and one manager can steer goals across many projects.

features

Mechanisms, not a feature list.

Eleven. Each one is an OS-like primitive, not a bullet.

01

Engine-driven loop

Idle + lease + 30s polling re-prompts the child with accumulated steering (progress + transcript tail + inbox). Not a parent re-prompt machine.

02

Scheduled intervals

scheduleEveryMs auto-requeues the same goal on an interval — 5s poll, skip-if-running, workspaceWrite gate, inbox Scheduled tick N/M.

03

Parent ↔ child

Owner tools inspect/steer; inbox injects into next turn. Wake-up on complete/block without polling.

04

Verified completion

Per-goal artifact isolation .opencode/loopd/goals/<id>/, maxTurns force-finish → semantic summary → parent notification.

05

Command sessions

Installs, builds, dev servers and REPLs as background processes with a fullscreen terminal — owner exit notifications, filter/until watches, timeouts. Never block the turn in bash.

06

Switch models mid-run

Provider hits quota? switch_goal_identity moves the goal to another model on the same worker — same transcript, progress, checks. Or configure ordered fallbackModels for automatic 429 failover.

07

Manual mode

interactive: true stops the engine from starting turns — every turn comes from your :send. For workers that wait for input.

08

Exact-file write tickets

Workers claim files before editing (claim_goal_scope). Disjoint tickets run in parallel; unclaimed writes are denied; no whole-workspace lock unless the objective names no files.

09

Wait queues & wakeup

Shells and writes that arrive while a ticket is held park instead of failing or spinning. Release paths wake parked work with inbox evidence; idle goals wake on complete/block.

10

Management mode

One manager session, many projects. directory param on loopd_create_goal runs a goal in another project; loopd_status_all aggregates across registered dirs; :projects in the TUI. Cross-dir goals default interactive. Fences are per-dir — no cross-talk.

11

Fence honesty

Denials name the exact holder (session, goal, files, age) instead of a generic busy message. await_quiescence parks the worker until clear; release paths fire parked awaits with inbox evidence. Owner shells never fence their own workers' writes.

architecture

How the loop runs.

OpenCode owns execution, queued delivery, session lifecycle. Loopd owns objectives, checks, budgets, scheduling, cross-goal coordination.

flowchart LR P["Main session / owner"] -->|create| G["Goal + worker session"] G --> T["Worker turn"] T --> I{"session idle?"} I -->|confirm 2s quiet| L["Release lease"] L --> E{"enforce limits"} E -->|continue| C["continueGoal: next prompt"] C --> T E -->|force finish| F["Force-finish prompt"] F --> T E -->|budget / blocked| X["blocked / budget_limited"] T -->|complete_goal / block_goal| Done["Terminal event"] Done --> N{"shouldNotifyParent?"} N -->|yes| Wake["host.notifyOwner wake-up"] Wake --> P S["Schedule worker 5s"] --> R["complete -> active, tick N/M"] R --> T M["Maintenance 30s"] --> Stuck["stuck / provider retry recovery"] Stuck --> T

Host execution stays owned by OpenCode. Loopd owns objectives, checks, budgets, scheduling, and wake-ups; the dashboard and owner tools keep the parent in control.

Each goal is a GoalID. The dashboard is a modal dialog that pushes loopd.dashboard onto the keymap so the chat prompt never sees your keys. Artifacts are namespaced per-goal. 1.7 adds a 5s schedule worker that requeues complete scheduled goals on interval with skip-if-running.

quick start

First goal in 30 seconds.

/goal fetch the latest AI news and save 10 items to ai-news.md
# agent clarifies → loopd_create_goal → child loops every ~30s

# Scheduled — one goal, auto-requeues on interval (1.7)
loopd_create_goal({
  name: "hourly-report",
  objective: "Append date -u to tick.txt each run",
  scheduleEveryMs: 3600000, // 1h
  scheduleMaxRuns: 24
})

compare

Why loopd vs. plain loop?

Plain /loop injects prompts into the main session — it pollutes the transcript. Codex goals keep history per-thread and steer via internal context. Loopd does the same for OpenCode.

opencode-loopd

Child session per goal, no transcript pollution, artifact isolation, scheduled requeue, parent wake-up injection.

Plain /loop

Single session, prompt injected into main chat, manual polling to see progress, no interval.

Codex / Claude Code

Inspiration: Codex goals keep per-thread history and steer via internal context — loopd adds scheduled intervals for repetitive dialogues.

concurrency

Like an OS scheduler, not a lock.

Write tickets, wait queues, wakeup. Goals do not spam retries; they park and get woken when the holder releases.

// 1. Claim the smallest useful file set before editing
claim_goal_scope({ paths: ["src/a.ts", "src/b.ts"], runGeneration })

// 2. Park when a ticket is held (no spin, no sleep)
await_quiescence()   // returns with inbox evidence when clear

// 3. Release paths fire parked awaits
// afterWorkspaceTool / operation end -> inbox "workspace released"

// 4. Exact conflicts fail fast with owner/path/age diagnostics
// kind: initial | expansion  -> coordinate_then_retry

Exact files, not globs or directories. Disjoint owners run in parallel; read-only goals never contend. Fences are per-directory stores, so management mode has no cross-talk. Parked work wakes with evidence instead of burning turns into evaluator rejections.

management mode

One manager. Many projects.

Run goals in other repos from one session. Standing goals per project keep developing; the manager watches and steers.

// Register target projects (absolute paths)
// ~/.opencode/loopd/managed.json  or  LOOPD_MANAGED_DIRS=/a:/b

// Create a goal in another project
loopd_create_goal({
  name: "fix-auth",
  objective: "fix the auth bug",
  directory: "/Users/you/Code/other-project",
  checks: ["npm test"]
})

// Aggregate view across all managed projects
loopd_status_all({})
// → per-dir totals + blocked items, each with its directory

// Steer a foreign goal (engines route by global session ID)
send_goal_input({ goal_id: "...", message: "use approach B" })
nudge_goal({ goal_id: "..." })

Cross-dir goals default interactive:true (manager-steered). Checks run from the target root. Fences are per-dir stores — no cross-talk. Goal IDs are UUIDs; always show the directory alongside.

faq

Questions.

How to run background agents in OpenCode?

Install @bojackduy/opencode-loopd as a plugin (both opencode.jsonc and tui.json), restart, then /goal in any session. The engine spawns a child worker that loops autonomously; you monitor with /loop.

Is this like Claude Code's loop or Codex goals?

Yes — same mental model: engine-driven idle → continuation steering with accumulated context → child calls complete_goal/block_goal → parent wake-up. Like Codex, but native to OpenCode's session model.

Where do loop outputs go?

Per-goal: .opencode/loopd/goals/<id>/ (e.g. progress.md). If your objective names ./reports/, that wins.

How to schedule repetitive tasks?

Use scheduleEveryMs — e.g. scheduleEveryMs: 60000 for 1m interval, scheduleMaxRuns: 10 for 10 total. The 5s schedule worker resurrects complete → active with Scheduled tick N/M inbox; workspaceWrite:true defers if another writer is active.

How to report a bug?

In the dashboard press Shift+B or :bug — opens github.com/bojackduy/opencode-loopd/issues/new prefilled with environment (version, OS, goal context).

What if my provider hits quota mid-run?

Run loopd_list_models to see what's connected, then switch_goal_identity to move the goal to another model — same worker, transcript and progress kept. Or set fallbackModels at creation for automatic ordered failover on 429s. Dashboard: :model / :models.

Can I run dev servers and long installs without blocking?

Yes — use command sessions (loopd_command_start) instead of the blocking shell: installs, builds, dev servers and REPLs run in the background with a fullscreen terminal, owner exit notifications, and until pattern watches that wake you when output appears.

How do multiple goals edit code without clobbering each other?

They claim exact files first (claim_goal_scope). Disjoint tickets run in parallel; overlapping claims fail fast with the owner, path, and age. Read-only goals set workspaceWrite: false and never contend. If a ticket is held, callers park with await_quiescence and wake with inbox evidence instead of spinning.

Can one session manage goals in other projects?

Yes — management mode. Register target directories, create goals with directory, and aggregate with loopd_status_all. Fences are per-directory, checks run from the target root, and cross-dir goals default to interactive so the manager steers each turn.
