## 1. What is each product for, and does its TUI solve the target user's need?

### Takeaway

Goal-plugin's one-sentence proposition is **“Keep this OpenCode session working toward one explicit goal, with persistent state, evidence, and automatic continuation.”** Loopd's is **“Delegate durable goals to separate OpenCode workers while retaining verified completion, bounded supervision, and an interactive parent conversation.”** They overlap in goal persistence and continuation but optimize different units of work: the current conversation versus an owner/worker system. These are analytical compressions of the documented promises. [Goal-plugin introduction and workflow](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/README.md#goal-workflow); [loopd README:3–5,18–26,30–41](../../README.md#L3-L41).

### Cited Findings

- **Goal-plugin's default workflow is session-local.** `/goal <objective>` creates a long-running goal in a fresh chat; replacing/clearing archives previous lifecycle state in the same thread. Automatic continuation is enabled by default and pinned to the tracked agent. Plan-created goals remain paused until the user changes mode and resumes. There is no separate mandatory worker-agent choice in the documented quick start. [Workflow](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/README.md#goal-workflow); [Plan Mode Safety](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/README.md#plan-mode-safety).
- **Loopd's default workflow is delegated.** The owner clarifies what/where/how to verify, creates a hidden child session, and inspects/steers it. README defaults are 50 turns, three consecutive failures, three no-progress turns, five-minute per-turn lease, `workspaceWrite: true`, `interactive: false`. The README explicitly says creation fails unless `agent` or `defaultAgent` is supplied. The assigned files do not establish automatic live-identity inheritance; do not substitute the user's broader harness policy for this documented package contract. [README:139–206,265–290](../../README.md#L139-L206); [defaults:265–290](../../README.md#L265-L290).
- **Goal-plugin TUI is an indicator and control surface, not the execution owner.** Sidebar displays status, elapsed time, tokens, continuation count, checkpoint, message, stop reason, objective; palette controls lifecycle. Its domain document explicitly separates server functionality from surface indicators, and treats slash commands as the web/desktop entrypoint. [README Notes](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/README.md#notes); [CONTEXT.md](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/CONTEXT.md).
- **Loopd TUI is a supervisory cockpit.** Goals/Commands tabs, modal NORMAL/INSERT interaction, worker-session opening, pause/resume/retry/clear, input, identity switching, and command terminals address simultaneous work and intervention. The README explicitly says the parent never needs the dashboard; owner tools can inspect and steer. [README:155–194](../../README.md#L155-L194).
- **Latest loopd positioning is supervision above native execution.** OpenCode owns execution, queued delivery, and session lifecycle; loopd owns objectives, acceptance checks, budgets, schedules, and file coordination. Native reconciliation uses host outcome/context/queue projections, while older hosts fall back to legacy heuristics. This is more specific than “another background-agent runner.” [README:30–41](../../README.md#L30-L41); [v2 supervisor:3–27,54–68](../../docs/v2-supervisor.md#L3-L27).
- **Competitor also documents native lifecycle integration.** Its Notes describe v2 execution-success events, native retry suppression, terminal-failure recovery, interruption behavior, and public session-wait integration. Calling it merely an idle-hook plugin would misrepresent the current README. [Notes and ACP boundaries](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/README.md#notes).

### Inferences

- For “finish this refactor in this chat,” goal-plugin's session-local mental model likely has lower initial conceptual burden. For “keep my chat free while checked work proceeds elsewhere,” loopd's separation is a meaningful benefit, not gratuitous complexity. Falsify this with identical tasks and record first successful creation, interruptions of the owner conversation, and number of lifecycle concepts the user must learn. [Workflow basis](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/README.md#goal-workflow); [loopd usage](../../README.md#L139-L206).
- A TUI solves **visibility and intervention**. It does not itself establish correct continuation, delivery, acceptance, or reservation release. For loopd, the decisive experience is trustworthy background completion and recoverable blockers; dashboard polish cannot substitute for those contracts. For goal-plugin, `/goal` plus accurate state can satisfy much of the cross-surface need without a full dashboard. These are product inferences, not measured usability outcomes. [loopd native ownership](../../docs/v2-supervisor.md#L3-L27); [competitor surface distinction](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/CONTEXT.md).

### Gaps

- No popularity, stars, downloads, conversion, or comparative defect-rate conclusions are made. There is no observed first-run usability test in this assignment.
- User-supplied incident history: repeated loopd stalls, false nudges, global-file-lock blocking of reads after scopes, and v1/v2 delivery mismatch. These are real reported incidents for this investigation, **not broad public quality statistics**. No public incident URLs or transcripts were provided, and the four-file scope cannot validate their causes or current fix status. Treat them as acceptance-test priorities for the separate source audit, not as proof that 1.14.2 still has each bug or that the competitor is more reliable.

## 2. What does onboarding actually require, and what is the first successful action?

### Takeaway

Goal-plugin documents a one-command v1 installation and version-specific v1/v2 configuration; loopd documents both a two-config plugin-only path and an installer that additionally provides `/goal` and the skill. Counting commands alone hides the critical difference: loopd's first useful delegated task also requires an agent/check contract, and modern scoped operation adds host capability requirements. ## 3. What ongoing friction matters, and what five improvements have the highest impact?

### Takeaway

Goal-plugin concentrates complexity in session lifecycle, safety limits, plans, and client adapters. Loopd adds valuable independent checks, scheduling, process management, and exact-file coordination, but users must understand more boundaries and recovery states. Highest leverage is to make trustworthy progress, compatibility, and recovery explicit before adding more UI surface. [Competitor workflow/notes](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/README.md#goal-workflow); [loopd usage](../../README.md#L155-L206); [loopd coordination](../../docs/file-scope-ownership.md#L99-L119).

### Cited Findings

Persistent plans add revisions, criteria, phases/tasks, evidence and scope-revisit rules. Simple start does not mean small total control surface. | Separate goal workers versus raw commands; owner tools versus worker protocol; `/goal`, `/loop`, `/commands`, modal keys, terminal keys, model/agent controls; scoped work adds claims/generations/check operations. ### Inferences

**Five high-impact recommendations, prioritized; all proposed, not implemented:**

1. **Gate the product promise on a reproducible lifecycle journey.** Acceptance: create → substantive child progress → steer while busy → wait through a real long tool/provider retry without false nudge → checks → exactly-once owner result; repeat across restart and supported delivery modes. Include the supplied stall/false-nudge incidents as regression scenarios, without inventing their root causes. Measure duplicate deliveries, false-stale decisions, completion/check disagreement and owner-delivery omissions before claiming improvement. Rationale: native reconciliation is already the documented contract; making its outcome dependable addresses the user's actual need more directly than more dashboard features. [Native fences and running state](../../docs/v2-supervisor.md#L18-L52).
2. **Publish one version/capability-aware first-success path.** Lead with the installer when `/goal` is expected; explicitly distinguish plugin-only capabilities. State server/TUI config entrypoints for each actually supported host, how to choose a worker agent, and a minimal meaningful checked goal. Distinguish SDK dependency ranges from tested CLI versions; expose native/legacy/unsupported-scope status in the first-use result. Acceptance: an unfamiliar user with clean supported configuration reaches an evidenced goal and receives owner notification by following one path, without discovering missing agent/command prerequisites later. [Install](../../README.md#L43-L135); [required agent/checks](../../README.md#L276-L290); [mode diagnostics](../../docs/v2-supervisor.md#L61-L64); [competitor version matrix](https://github.com/prevalentWare/opencode-goal-plugin/blob/9c52be63da06829d55e3e0b7a6580223312765b1/README.md#install).
3. **Make coordination recovery actionable and preserve exploration.** Explain three contracts together: artifact-only/read-only, explore-then-claim, legacy exclusivity. Conflicts should identify path/owner and the permitted next action; distinguish scope conflict, active verification reservation, closing in-flight work, and orphan fence. Acceptance scenarios: protected goal still reads/searches; disjoint owners progress; overlapping edit denied; failed check/tool drains correctly on supported v2; read-blocking reproduction resolved; real crash remains honestly fenced. Do not recommend automatic unlock without proof of drain. [Scope contracts/workflow](../../docs/file-scope-ownership.md#L3-L40); [read/search and checks](../../docs/file-scope-ownership.md#L50-L60); [restart/fences](../../docs/file-scope-ownership.md#L77-L119).
4. **Sell checked delegation and honest execution state, then align the docs.** Put “OpenCode executes; loopd verifies/supervises” and a single owner/worker example ahead of legacy loop metaphors. Qualify same-worker and serialization claims; place `write_scope` beside `workspaceWrite`; distinguish completed execution, passed checks, evidenced completion, and forced completion in explanations/status. Acceptance: README, defaults table, dashboard labels and architecture docs tell the same native/legacy/scoped story. This reduces cognitive burden without abandoning loopd's differentiation. [Positioning](../../README.md#L3-L5); [native ownership](../../docs/v2-supervisor.md#L3-L5); [old loop wording](../../README.md#L238-L241); [scope lifecycle](../../docs/file-scope-ownership.md#L107-L119); [force bypass](../../README.md#L328-L332).
5. **Make budget and stop/resume consequences legible before scheduling or recovery.** Explain actual default limits, whether checks/forced reports/retries count, remaining allowance, schedule run count, and what a pause can still leave in flight. Do not label turn limits dollar caps; default-unlimited scheduling deserves explicit confirmation in the task contract rather than surprise.
